APP DE PRÉSTAMOS PERSONALES
Resumen técnico y lógica de negocio
======================================

1. OBJETIVO
-----------
Crear una aplicación para administrar préstamos personales realizados a clientes/amigos, reemplazando el control actual en Excel.

La app debe permitir:
- Registrar clientes.
- Crear préstamos.
- Registrar pagos parciales o totales.  
- Calcular saldos automáticamente.
- Renovar préstamos descontando deuda pendiente.
- Mantener historial completo de movimientos.
- Mostrar un resumen general de cartera.
- Evitar editar manualmente saldos calculados.

La app NO incluye por ahora la gestión personal de ingresos y egresos.


2. MODELO PRINCIPAL
-------------------
La estructura lógica será:

CLIENTE
  -> PRÉSTAMOS
       -> PAGOS / MOVIMIENTOS
       -> RENOVACIONES

Un cliente puede tener uno o varios préstamos a lo largo del tiempo.

Cada préstamo pertenece a un único cliente.

4. REGLAS DE CÁLCULO
--------------------

4.1 Préstamo normal

Ejemplo:
Monto prestado: S/ 500
Interés: 20%

monto_interes =
    monto_base * porcentaje_interes / 100

total_a_cobrar =
    monto_base + monto_interes

Resultado:
Monto base: S/ 500
Interés: S/ 100
Total a cobrar: S/ 600
Monto desembolsado: S/ 500


4.2 Saldo pendiente

saldo_pendiente =
    total_a_cobrar
    - suma(pagos_normales)
    - suma(compensaciones_validas)

El saldo NO debe almacenarse como un valor editable.

Debe calcularse a partir de los movimientos del préstamo.


4.3 Total pagado

total_pagado =
    suma de pagos aplicados al préstamo


4.4 Ganancia por interés

ganancia_teorica =
    total_a_cobrar - monto_base

La aplicación también puede calcular:

ganancia_realizada =
    parte de intereses ya efectivamente cobrada

Esto puede agregarse más adelante si se necesita separar recuperación de capital e interés.


5. LÓGICA DE RENOVACIÓN
-----------------------

La renovación es una operación especial.

Caso:

Saldo pendiente del préstamo anterior:
S/ 100

Cliente solicita un nuevo préstamo:
S/ 500

Entonces:

nuevo_monto_base = S/ 500
saldo_anterior = S/ 100

monto_real_entregado =
    nuevo_monto_base - saldo_anterior

Resultado:
Monto del nuevo préstamo: S/ 500
Deuda anterior compensada: S/ 100
Dinero realmente entregado: S/ 400

Si el interés del nuevo préstamo es 20%:

interes = S/ 100
total_nuevo_a_cobrar = S/ 600


IMPORTANTE:

El préstamo anterior NO debe registrarse como si el cliente hubiera pagado S/ 100 en efectivo.

Debe registrarse:

COMPENSACION_POR_RENOVACION: S/ 100

Luego:
- El préstamo anterior queda con saldo S/ 0.
- Su estado pasa a RENOVADO.
- Se crea un nuevo préstamo.
- El nuevo préstamo mantiene trazabilidad hacia el préstamo anterior.


6. VALIDACIONES DE RENOVACIÓN
-----------------------------

Antes de renovar:

- El cliente debe tener un préstamo activo.
- Debe existir un saldo pendiente mayor a 0.
- El nuevo monto solicitado debe ser válido.

Caso normal:

nuevo_monto > saldo_anterior

Ejemplo:
Solicita S/ 500
Debe S/ 100
Se entregan S/ 400.


Si:

nuevo_monto == saldo_anterior

Entonces:
- El desembolso real sería S/ 0.
- Se debe pedir confirmación o bloquear según la regla de negocio final.


Si:

nuevo_monto < saldo_anterior

Ejemplo:
Debe S/ 500
Solicita S/ 300

No se debe procesar como renovación estándar.

La app debe:
- bloquear la operación, o
- manejarla como pago/reestructuración especial.

Para la primera versión, lo recomendable es bloquearla.


7. REGISTRO DE PAGOS
--------------------

Al registrar un pago:

1. Seleccionar cliente.
2. Seleccionar préstamo activo.
3. Ingresar monto.
4. Ingresar fecha.
5. Seleccionar método de pago.
6. Confirmar.

Validaciones:

- monto > 0
- monto <= saldo pendiente

Si el pago es igual al saldo:
- saldo final = 0
- préstamo pasa a PAGADO

Si el pago es menor:
- préstamo continúa ACTIVO

No se debe permitir que un pago deje saldo negativo.


8. PRÉSTAMOS MÚLTIPLES
----------------------

Un cliente puede tener varios préstamos históricos.

Por defecto, la app debe distinguir:

- préstamos pagados
- préstamos activos
- préstamos renovados
- préstamos vencidos

Recomendación para primera versión:
permitir solo un préstamo ACTIVO principal por cliente.

Un nuevo préstamo mientras existe otro activo debería:
- tratarse como RENOVACIÓN, o
- requerir una confirmación especial.

Esto evita ambigüedad al aplicar pagos.


9. HISTORIAL
------------

Cada cliente debe mostrar una línea de tiempo.

Ejemplo:

Total: S/ 1,200

11/07/2026
Pago
S/ 150

17/07/2026
Pago
S/ 300

29/08/2026
Pago
S/ 150

30/08/2026
Renovación
Saldo anterior compensado: S/ 100
Nuevo préstamo: S/ 500
Monto entregado: S/ 400

No se recomienda eliminar movimientos históricos.

Si existe un error:
- anular
- revertir
- registrar ajuste

Esto conserva la trazabilidad.


10. RESUMEN GENERAL
-------------------

El dashboard puede calcular:

TOTAL POR COBRAR
=
suma de saldos pendientes de préstamos activos


TOTAL PRESTADO
=
suma de monto_base de préstamos


TOTAL DESEMBOLSADO
=
suma de monto_desembolsado

Este valor es especialmente importante por las renovaciones.


TOTAL COBRADO
=
suma de pagos normales recibidos


INTERÉS GENERADO
=
suma de monto_interes


CLIENTES CON DEUDA
=
clientes con saldo pendiente > 0


PRÉSTAMOS ACTIVOS
=
préstamos con estado ACTIVO


11. DIFERENCIA IMPORTANTE ENTRE MONTOS
--------------------------------------

La app debe manejar por separado:

MONTO BASE
Valor sobre el que se genera el nuevo préstamo.

MONTO DESEMBOLSADO
Dinero que realmente salió.

TOTAL A COBRAR
Monto base + interés.

SALDO PENDIENTE
Lo que todavía falta cobrar.

Ejemplo renovación:

Monto base: S/ 500
Saldo anterior compensado: S/ 100
Monto desembolsado: S/ 400
Interés: S/ 100
Total a cobrar: S/ 600


12. INTERÉS
-----------

El porcentaje habitual es 20%.

Sin embargo, NO debe estar fijo en código.

Debe ser:

- configurable
- editable por préstamo
- inicialmente prellenado con 20%

Esto permite usar:
- 10%
- 15%
- 20%
- otro porcentaje

sin modificar el sistema.

14. REGLAS DE INTEGRIDAD
------------------------

- Nunca modificar manualmente el saldo.
- Nunca borrar pagos físicamente en producción.
- Nunca borrar préstamos con movimientos asociados.
- Utilizar soft delete o estados de anulación.
- Guardar created_at y updated_at.
- Usar transacciones de base de datos en operaciones críticas.
- La renovación completa debe ejecutarse dentro de una sola transacción.


15. TRANSACCIÓN DE RENOVACIÓN
-----------------------------

La renovación debe ser atómica.

Pseudo flujo:

BEGIN TRANSACTION

1. Obtener préstamo activo.
2. Calcular saldo pendiente actual.
3. Validar nuevo monto.
4. Registrar compensación por renovación.
5. Marcar préstamo anterior como RENOVADO.
6. Crear nuevo préstamo.
7. Guardar prestamo_origen_id.
8. Registrar movimiento de renovación.

COMMIT

Si algún paso falla:

ROLLBACK

Así nunca puede quedar:
- el préstamo anterior cerrado
- pero el préstamo nuevo sin crear

20. PRINCIPIO GENERAL DEL SISTEMA
---------------------------------

El sistema no debe guardar solamente "cuánto debe una persona".

Debe guardar todos los hechos que llevaron a ese saldo:

- cuánto se prestó
- cuánto se cobró
- cuándo se cobró
- cuánto interés se aplicó
- cuánto se entregó realmente
- si existió renovación
- qué deuda anterior se compensó

El saldo debe ser el RESULTADO de esos movimientos.

Esto permite que la información sea auditable, confiable y fácil de ampliar posteriormente.


21. FUERA DEL ALCANCE INICIAL
-----------------------------

- ingresos y egresos personales
- contabilidad personal completa

- integración Yape/Plin

- múltiples usuarios/roles complejos

Pueden agregarse posteriormente.
